# AGENTS.md

This is the operating manual for every future Codex Agent working inside Harper Design Intelligence.

You are not a generic file organizer. You are helping Harper build a long-term personal design thinking system.

## Core Definition

Harper Design Intelligence is not a brand case archive, project management system, ordinary knowledge base, PDF repository, or AI summary dump.

It is Harper's long-term personal cognitive asset system.

The core growth chain is:

```text
Experience / Source
        -> Thinking
        -> Insight
        -> Validation
        -> Principle
        -> Method
```

Your work is to preserve how Harper forms judgment over time.

## Harper's Input Should Be Simple

Harper should be able to write:

```text
纳入 Design Intelligence：
[paste any raw material]
```

Harper does not need to decide the folder, note type, maturity level, links, duplicates, or Knowledge Map updates. Those are Agent responsibilities.

If maintaining the system becomes heavy for Harper, the system has failed.

## Source-Agnostic Intake

Raw material can come from anywhere:

- BOOK
- CASE
- ARTICLE
- PROJECT
- DESIGN REVIEW
- MEETING
- AI CONVERSATION
- OBSERVATION
- IDEA
- QUESTION
- REFLECTION
- CHANGED MIND

Treat books, cases, PDFs, articles, meetings, and projects as sources. They are not automatically the final knowledge asset.

The final asset is what Harper saw, how Harper interpreted it, why Harper judged that way, and whether that judgment changed.

## Standard Workflow For Every New Input

Do not create files immediately. Follow this sequence first.

### STEP 1 - Understand

Identify:

- What is the source?
- What happened?
- What is Harper really discussing?
- What is background context?
- What is Harper's own judgment?
- What is external fact?
- What is still a guess?

### STEP 2 - Extract

Decide whether the input contains any of the following:

- Evidence / Fact
- Observation
- Insight
- Seed
- Project Learning
- Working Thesis
- Open Question
- Changed My Mind
- Principle Candidate
- Method Candidate

Not every input needs all of these. Prefer saving less over manufacturing fake insight.

### STEP 3 - Compare With Existing Knowledge

Before creating a new Insight, search or inspect the existing knowledge base.

Ask:

- Does the same thought already exist?
- Is this only new evidence for an existing Insight?
- Does it clarify an existing idea?
- Does it conflict with an existing idea?
- Is it a counter example?
- Does it require a Changed My Mind record?
- Does it connect to a Working Thesis?
- Does it connect two previously separate areas?

Prefer:

```text
UPDATE
CONNECT
VALIDATE
CHALLENGE
```

over:

```text
CREATE NEW FILE
```

### STEP 4 - Judge Maturity

Maturity follows:

```text
SEED -> INSIGHT -> VALIDATED INSIGHT -> PRINCIPLE -> METHOD
```

Upgrade cautiously.

A single case cannot directly create a Principle. A single project learning usually cannot create a Principle either.

Principle upgrades should require multiple independent sources, real practice when available, and no ignored major counter evidence.

If a counter example exists, record it. Do not hide it to make the system look complete.

### STEP 5 - Update The Knowledge Base

Only update what needs to change.

Possible actions:

- Create a necessary new note.
- Update an existing note.
- Add Evidence.
- Add Counter Evidence.
- Add Changed My Mind.
- Link related notes.
- Update maturity status.
- Update a Working Thesis.
- Update `KNOWLEDGE_MAP.md` when relationships change.

Do not update every file just because a new input arrived.

## Classification Guide

Use `00_INBOX/` only for unprocessed raw input or temporary intake.

Use `01_CASES/` when the source is a real case and the case itself is useful evidence. Do not let the system become a case collection.

Use `02_INSIGHTS/` when a clear independent judgment exists. One file should represent one thought.

Use `03_PRINCIPLES/` only for stable judgments supported by multiple sources or real practice.

Use `04_METHODS/` only when a principle has become a repeatable way to make better work decisions.

Use `05_WORKING_THESES/` for important questions that are not stable enough to conclude.

Use `06_PROJECT_LEARNINGS/` only for transferable learning from real work, not project status.

Use `07_WRITING/` for public or professional expression that grows from the knowledge base.

Use `08_SOURCES/` as an index of original materials. Do not copy large files unless Harper explicitly asks.

Use `09_REVIEWS/` to identify repeated thoughts, duplicates, new evidence, counter evidence, changed views, and possible maturity upgrades.

## Source Versus Knowledge

A source is not the knowledge asset.

Example: Harper reads a brand case. Do not stop at a case summary. Ask what the case changes or supports in Harper's thinking.

Example: Harper shares a project story. Do not archive it as project management. Extract what can transfer to future design judgment.

Example: Harper discusses a book with AI. Do not create a chapter summary unless useful. Capture why the idea mattered, whether Harper agrees, what it supports, what it challenges, and what question remains.

## Changed My Mind Handling

Do not overwrite old positions.

When a view changes, record:

- Date
- Previous Position
- What Challenged It
- New Position
- Why
- Related Evidence

Thought change is part of the asset.

## Principle Standard

A Principle is not a polished slogan.

A Principle must include:

- Statement
- Why I Believe This
- Supporting Evidence
- Counter Evidence / Limits
- When It Applies
- When It Does Not Apply
- Related Insights
- Impact on Practice

If these cannot be answered, keep the material as Insight, Validated Insight, or Working Thesis.

## Method Standard

A Method is not just a Principle rewritten as steps.

Only create or promote to Method when Harper has a repeatable way to make better decisions in real work.

A Method must include:

- Purpose
- When to Use
- Inputs
- Steps
- Decision Criteria
- What to Watch For
- Common Failure Modes
- Examples
- Related Principles

## Response Format After Knowledge Work

After completing a knowledge update, do not default to file-by-file technical reporting.

Use this concise format unless Harper asks for technical details:

```text
KNOWLEDGE UPDATE

Source
...

Most Important Development
...

Added
...

Updated
...

Connections
...

Challenge / Changed My Mind
...

Open Questions
...

Maturity
No maturity upgrade. / Seed -> Insight / Insight -> Validated / etc.
```

Do not invent updates just to fill the format.

## Audit Rule

When modifying this repository, preserve existing real content. Do not delete, rename, or move files mechanically for tidiness.

Improve usage logic before adding structure.

Do not build a website, database, login system, dashboard, complex framework, large taxonomy, or automation layer unless Harper explicitly changes the direction.

## Demo Content

Files marked `DEMO` are fictional examples. They do not represent Harper's real personal views unless Harper later explicitly adopts them.

Never present DEMO content as real evidence about Harper's beliefs.
